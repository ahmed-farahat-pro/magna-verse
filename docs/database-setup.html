The database, and how to start

MagnaVERSE today is one desktop, one machine, no login — and none of its data survives a browser. This is what to build so that people sign up, keep several workspaces, and find their own documents, settings and files waiting for them on any machine. It is written for two developers working in parallel, with the seam between them specified before either starts.

Who builds what

Where every piece of data lives

Not everything belongs in Postgres. This split is what keeps the desktop fast and — more importantly — keeps a stolen database backup from being a stolen credential set.

StoreHoldsWhy there
Postgres
Supabase		 profiles, workspaces, memberships, settings, documents, sheets, file metadata, mail metadata, workflows, activity journal, and the whole rag schema Needs row-level security, needs to be queryable, and needs to follow the user to a second machine
Supabase Storage file bytes — the actual .docx, .xlsx, .pdf Blobs do not belong in rows
Local $DSH_HOME
per user, on the server		 credentials, dsh session transcripts, the agent's working directory, caches See the box below

Credentials never enter Postgres

Mail passwords, GitHub tokens and Microsoft refresh tokens stay in the harness credential store inside that user's own directory. The database holds only a secret_ref — the name of a token, never its value. This is already how app-connections works and it must not change: it means a database backup that leaks contains no live tokens at all. That is a property worth defending on purpose rather than discovering you have lost.

What has to move out of the browser

Everything below is localStorage today and dies with a browser profile:

  • 25 mv7.* preference keys — theme, wallpaper, dock contents and position, window layout, icon coordinates, widgets per space, focus mode, notification style, wake word. These become app.user_settings, which is what makes someone's desktop look like their desktop on a second machine.
  • mv7.vfs — the entire file system as one JSON blob, with no owner field and folder ids hardcoded as the literals "desktop" and "docs-folder". Two users' trees would collide on those ids the moment they shared a store.
  • Nine app plugins have no durable storage at all — Docs, Sheets, Brain, Ledger, Approvals, Models, Trajectory, Terminal and Market are an in-memory Map, lost on every restart. Docs and Sheets are precisely the apps whose per-workspace content you want.

The shape of the system

dsh refuses to be a network service, and it is right to

dsh-web-app/lib/startup.js:39
  --host 0.0.0.0 is intentionally not supported yet for safety:
  it would expose remote code execution to the network

Behind that refusal: no auth package, no user, no account — zero matches for cookie across the entire harness. Loopback is the authorisation model; anything reaching a child's port has full privilege including credentials.set and host.openPath. So the gateway is not a convenience, it is the whole security boundary. Bind children to 127.0.0.1, never publish those ports, and treat a gateway auth bug as total compromise.

The schema

Three schemas. auth belongs to Supabase and you never write to it. app is yours. rag is your colleague's.

The core tables

create schema app;
create extension if not exists vector;     -- your colleague needs this
create extension if not exists pgcrypto;

-- Mirror of auth.users. Never duplicate the password: auth.users.encrypted_password
-- is GoTrue's bcrypt hash and we neither read it nor reimplement it.
create table app.profiles (
  id           uuid primary key references auth.users on delete cascade,
  email        text not null,
  display_name text,
  locale       text default 'en',
  created_at   timestamptz default now()
);

create table app.workspaces (
  id         uuid primary key default gen_random_uuid(),
  name       text not null,
  slug       text unique,
  owner_id   uuid not null references auth.users on delete cascade,
  created_at timestamptz default now()
);

create table app.memberships (
  user_id      uuid not null references auth.users on delete cascade,
  workspace_id uuid not null references app.workspaces on delete cascade,
  role         text not null default 'member'
               check (role in ('owner','admin','member','viewer')),
  primary key (user_id, workspace_id)
);

-- The desktop's own preferences: the 25 mv7.* keys that live in localStorage today.
create table app.user_settings (
  user_id uuid not null references auth.users on delete cascade,
  key     text not null,
  value   jsonb not null,
  primary key (user_id, key)
);

-- File TREE and metadata. The bytes live in Supabase Storage; storage_path points at them.
create table app.files (
  id           uuid primary key default gen_random_uuid(),
  workspace_id uuid not null references app.workspaces on delete cascade,
  parent_id    uuid references app.files on delete cascade,
  name         text not null,
  kind         text not null check (kind in ('file','folder')),
  ext          text default '',
  size         bigint default 0,
  storage_path text,                       -- null for folders
  content_hash text,                       -- lets ingestion skip unchanged files
  deleted_at   timestamptz,                -- soft delete, so Trash works
  created_at   timestamptz default now(),
  modified_at  timestamptz default now()
);

create index on app.files (workspace_id, parent_id) where deleted_at is null;

Give every new user a workspace, in the same transaction

A user with no workspace is a broken state — the first login lands on a desktop with nowhere to put anything. Create it in the signup trigger, not in application code that might not run.

create function app.handle_new_user() returns trigger
  language plpgsql security definer as $$
declare ws uuid;
begin
  insert into app.profiles (id, email, display_name)
    values (new.id, new.email, split_part(new.email, '@', 1));

  insert into app.workspaces (name, owner_id)
    values ('Personal', new.id)
    returning id into ws;

  insert into app.memberships (user_id, workspace_id, role)
    values (new.id, ws, 'owner');

  return new;
end $$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function app.handle_new_user();

Creating the database, step by step

Migrations are numbered SQL files checked into the repo under supabase/migrations/ and applied in order. Never a schema edited by hand in the dashboard — the next environment has to be reproducible from the repo alone, and a hand-edit is a change nobody can review or replay.

1
Create the project

One Supabase project per environment — magna-dev and magna-prod, never one shared. Pick the region closest to Riyadh that is offered. Save the database password somewhere real; it is shown once.

2
Install the CLI and link it 
npm install -g supabase
supabase login
supabase init                 # creates supabase/ in the repo
supabase link --project-ref <your-project-ref>
3
Write the migrations in this order

Split so that a failure is legible and a merge conflict is local to one concern. Your colleague uses a separate number range so your files and his never collide.

000_extensions.sqlvector, pgcryptoyou
001_schemas.sqlapp, rag, and the is_member helperyou
002_identity.sqlprofiles, workspaces, memberships, the signup triggeryou
003_settings.sqluser_settings, workspace_settingsyou
004_content.sqlfiles, documents, sheetsyou
005_apps.sqlmail, workflows, connections, activityyou
006_rls.sqlenable RLS and add every policyyou
007_storage.sqlthe workspace-files bucket and its policiesyou
100_rag.sqldocuments, chunks, entities, edgescolleague
4
Apply and verify 
supabase db push                       # apply to the linked project
supabase db reset                      # locally: replay every migration from zero

db reset is the one that matters. If a full replay from an empty database does not produce a working schema, the migrations are already broken — you just cannot see it yet.

5
Configure Auth

Email + password on. Email confirmations on. Set the site URL and redirect URLs to the gateway, not to localhost:3080 — the desktop is behind the gateway now. Set the JWT expiry short (an hour) and rely on refresh; the cookie carries both.

6
Wire the keys — in exactly one place 
# .env  (git-ignored)
SUPABASE_URL=https://<ref>.supabase.co
SUPABASE_ANON_KEY=eyJ...            # safe in the gateway and in plugins
SUPABASE_SERVICE_ROLE_KEY=eyJ...    # GATEWAY ONLY — never in a plugin

One config module reads these. No other file in the repo names a Supabase URL — that is what keeps moving to a self-hosted Supabase inside your own DC a deployment change rather than a rewrite.

The wall: Row Level Security

This is the part that actually keeps one company's documents away from another's. Application code that says where workspace_id = ? is a filter that one forgotten line removes. RLS is a wall the database enforces whether or not the application remembers.

-- One helper, security definer, so policies never recurse (see the traps below).
create function app.is_member(ws uuid) returns boolean
  language sql security definer stable as $$
  select exists (
    select 1 from app.memberships
    where workspace_id = ws and user_id = auth.uid()
  );
$$;

-- Then every workspace-scoped table gets the same four lines.
alter table app.documents enable row level security;

create policy "read"   on app.documents for select using (app.is_member(workspace_id));
create policy "write"  on app.documents for insert with check (app.is_member(workspace_id));
create policy "update" on app.documents for update using (app.is_member(workspace_id));
create policy "delete" on app.documents for delete using (app.is_member(workspace_id));

-- Settings are per USER, not per workspace, so they key on auth.uid() directly.
alter table app.user_settings enable row level security;
create policy "own settings" on app.user_settings
  for all using (user_id = auth.uid()) with check (user_id = auth.uid());

Turn RLS on before the first row exists

Retrofitting it onto a populated table is where tenancy bugs are born, because every test you would write to catch the gap passes against data that was inserted before the wall went up. A table created without RLS in the same migration that creates it is a table that will be shipped without RLS.

Each user's files

You asked for every user to have their own storage — files and folders. There are two distinct things wearing that name, and conflating them will cost you a week.

Their documents

Metadata in app.files, bytes in Supabase Storage. The tree, names, folders and soft-deleted Trash live in Postgres so they are queryable and RLS'd. The bytes go in a workspace-files bucket at <workspace_id>/<file_id>.

This is what the Files app shows, what Docs and Sheets write to, and what ingestion reads. It follows the user to any machine.

The agent's working directory

A real folder on the server, inside that user's $DSH_HOME. When a workflow runs a shell command or the sys.write node writes a file, it happens here — on a real filesystem, because that is what a shell needs.

Not synced, not in Postgres, and isolated per user by the DSH_HOME boundary that already exists.

-- The bucket, and a policy that mirrors the table's
insert into storage.buckets (id, name, public) values ('workspace-files', 'workspace-files', false);

create policy "members read files" on storage.objects for select
  using (
    bucket_id = 'workspace-files'
    and app.is_member( (storage.foldername(name))[1]::uuid )   -- first path segment is the workspace
  );

How the desktop connects

One module in @magna/os knows the URL. Everything else asks it.

// packages/os/lib/supabase.js — the ONLY file that names the URL
import { createClient } from "@supabase/supabase-js";

export function clientFor(tenant) {
  return createClient(process.env.SUPABASE_URL, process.env.SUPABASE_ANON_KEY, {
    // The user's own JWT, so every query is subject to RLS as that user.
    // Never the service-role key: it bypasses RLS and nothing would tell you.
    global: { headers: { Authorization: "Bearer " + tenant.jwt } },
    auth: { persistSession: false },
  });
}

Three small changes in packages/os unlock all of this, and the first is one line:

  • registry.js:275 calls handler(command, args) — so the fourth argument invoke() already accepts never reaches an app. Forward it and every app becomes workspace-aware.
  • scopeFor(appId) at registry.js:127 is the choke point every app's handle comes from. Add the workspace there and an app cannot read another's.
  • http.js:192 invokes with no context at all. The gateway injects a header; the OS route reads it and passes { userId, workspaceId } through.

Four traps

1 · RLS on memberships recurses

A policy on app.memberships that reads app.memberships to decide access is infinite recursion, and Postgres reports it at query time rather than at migration time — so it ships. Route every policy through the one security definer helper above.

2 · The service-role key in a plugin

It bypasses RLS completely and fails silently — everything works, every test passes, and every workspace can read every other. Grep for it in CI: it must appear nowhere under packages/.

3 · workspace_id taken from the request body

It must be derived server-side from the session cookie. The OS already learned this once: scopeFor stamps appId from the registration rather than from the caller, precisely because attribution a caller can set is attribution a plugin can forge.

4 · Process-per-user is the scaling ceiling

Measure the memory of one idle dsh child in week one. If it is 150 MB, a 32 GB machine holds roughly 200 idle users and far fewer active ones. That number decides whether this design survives a real customer list, and it is much cheaper to learn now than after launch.
