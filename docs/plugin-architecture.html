Proposed architecture · 19 August 2026

The OS is a plugin. The apps are plugins. The harness sees all of it.

MagnaVERSE Console stops being an app that calls DeepSeek Harness over HTTP, and becomes a plugin that runs inside it. Apps like Docs, Sheets and the code editor become plugins in turn — installable and removable one at a time. The reason to invert it is the last line of the stack: a harness that only receives chat prompts can never build a session brain, but one that sits under the whole desktop can.

01

The three layers

Read it bottom-up. Each layer only ever talks to the one directly beneath it, and every registration is reversible — which is what makes the top layer removable at runtime.

This removes a problem rather than adding one Verified

A browser at localhost:3000 calling 127.0.0.1:3080/api gets a hard 403. The harness refuses sec-fetch-site: cross-site, requires Origin to equal Host, and sends no CORS headers at all — none of it configurable. Serving the desktop from inside dsh makes it same-origin, so fetch('/api/…') and new WebSocket('/api/events.mux') simply work. No proxy, no custom Node server, no Next.js.

Why removal actually works

Every registration in the harness goes through ctx.effect(fn, label), which returns the exact disposer for whatever that work created and binds it to the calling fiber. Disposal runs in strict LIFO and is idempotent. So uninstalling Docs is not a flag that hides a menu item — it disposes the route, the tools, the manifest row and the dock entry in one pass, and the agent's catalog shrinks with it.

03

What happens on install — and on removal

There is no Magna-specific machinery in this path. It is the harness's own plugin flow, which exists because dsh was built expecting third-party packages: the CLI subcommand accepts local directories, and ~/.dsh/profiles/node_modules is a symlink farm over the whole dependency closure specifically so out-of-tree plugins can resolve the service packages they name.

packages/app-docs/package.json — the two fields that matter
{
  "name": "@magna/app-docs",
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" }
  },
  "peerDependencies": {
    "@deepseek-ai/cordis":     "^4.0.1",
    "@deepseek-ai/dsh-tools":  "^0.1.0-rc.7"
  }
}

Peer dependencies rather than direct ones, deliberately: Node's parent walk resolves them out of ~/.dsh/profiles/node_modules, so the plugin binds to the harness the user is actually running instead of shipping a second copy of it.

04

How the brain gets built

Two paths, in opposite directions. The agent-side one is free — the harness already records every tool call, message and approval into an append-only session log, and a listener on a plain host context sees every session. The human-side one is the part we add, and it is the whole reason for putting the OS underneath rather than beside.

A human action reaching the model

This path does not exist today at all. In the current console, app code calls toast() 83 times and emits to the event bus zero times — so an agent watching the bus sees nothing a person does in Sheets, Files or Docs. Routing every mutating host-API call through one observe point is the single change that turns the brain on.

An agent action reaching the desktop

The mirror image, and mostly free. The tool pipeline already runs pre-policy, guarded dispatch, post-policy and result observation, and the approval seam already fails closed when no answerer is present. The console's existing requestApproval needs no signature change — it already renders in-window when it knows which window, and floats when it does not.

05

Who owns what

The boundaries matter more than the boxes. A plugin that can reach the theme engine or the desktop repaint is not a plugin — it is a patch with extra steps.

The one habit that has to change

Today w.state is used 325 times as private scratch and as a cross-window back channel — apps publish functions onto it that other apps then call directly. That cannot survive a plugin boundary, and replacing it with a named command surface is what lets the same call work whether a person or the agent made it.

07

Three real limits — and whether any of them blocks the brain

The goal is specific: the harness collects everything every plugin does, and builds one picture of the session from it. So the only question worth asking about each limit is whether it stops that. The short answer is that none of the three do — but working through why surfaces one architectural decision that does have to be made, and it is not obvious.

LimitWhat it actually stopsBlocks the brain?What we do instead
Closed event vocabulary
43 types, generated		 Writing a magna/app-action event into the session log and having it replay as a first-class fact. The read path refuses unknown types. No Fine-grained state lives in a projection; model-visible facts go through agent.inject(), which lands as request/context — an existing type whose entire purpose is injected context. This is the supported channel, not a detour around a locked door.
Closed mux frame union
9 members, private broadcast		 Pushing a frame of our own shape down the socket the harness already owns. No session/projection carries an untyped value — the designed escape hatch — and registering a projection gets it broadcast automatically. Anything too chatty for the session log goes on our own upgrade route instead.
Flat tool namespace
duplicates throw		 Two apps registering open — the second one throws and fails to load. No for us
Later for a marketplace		 Prefixing by owner is enough while we write all the apps. The moment third parties publish, a convention is not enough — so the OS rejects a manifest at registration whose declared tools do not start with its own id. An invariant, not a guideline.

The decision this forces: the brain needs two stores, not one

Because plugin activity cannot be a session event type, the obvious move is to put it all in a session projection. That works — projections are durable, replayable, cached for cold reads, and pushed to the browser for free. But a projection is scoped to one session, and that scoping has a consequence that is easy to miss until it bites:

Work with no conversation open has nowhere to go

Someone spends an hour in Sheets and Files without opening Chat. There is no session, so there is no projection, so the entire hour is invisible. Then they open Chat and ask "what was I just doing?" — and a brain built only on session projections has no answer, because from the harness's point of view nothing happened.

What could actually stop this

None of the three published limits is the real risk. These are.

Risk 01

Volume drowns the context

Every keystroke is an action. Pushing all of them at the model destroys the context window and buries the signal — a brain that reports everything is as useless as one that reports nothing.

The rule: the projection holds the fine detail, the prompt gets a summary. systemPrompt.context() renders current state — what is open, what has focus — and agent.inject() is reserved for facts that change an answer.

Risk 02

Forgeable attribution

Once a marketplace exists, any installed plugin can call the action bus. If it can also name which app it is, one bad plugin can write history in another app's name — and a brain confidently wrong about who did what is worse than no brain.

The rule: the OS stamps appId from the registration and never reads it from the caller. Each app gets a scoped handle that cannot claim to be another. Built

Risk 03

Compaction eats the memory

Long sessions get compacted, and injected context is exactly the kind of material a summariser drops first. The brain would quietly lose its oldest and often most useful observations.

The rule: the durable store is the source of truth, never the transcript. Anything the model needs must be re-derivable from the projection and the workspace store on the next turn, not remembered from the last one.

So the answer to "can the harness see everything?" is yes Verified

The agent half needs no work at all — one ctx.on('session/event') listener on a host context receives every tool call, message, approval and turn boundary, in every session, and this is already running. The human half is ours to build, and the only thing the limits change is where it is stored, not whether it can be collected.

08

The staged path

Staged deliberately as insurance. If this stops after stage 1 you have a working sovereign desktop on a real local agent; if it stops after stage 2 you have that plus a proven plugin contract. Nothing here is only valuable once everything is finished.

Stage 0 · 2–3 days

The skeleton loads

One package with the activation field, a service, a /desktop route, and a listener that logs every session event.

  • You see: the profile lists @magna/os as a layer, /desktop serves our HTML, and the terminal narrates every event while you use the stock dsh UI in another tab.
  • De-risks: the entire premise, before a line of porting.
Stage 1 · 1–2 weeks

The console, on the real agent

Serve the existing console essentially as-is, then wire exactly one seam: chat streaming, a stop button, and tool approvals.

  • You see: the desktop you already know, with Chat talking to the local model — streaming token by token, stoppable mid-turn, and pausing for approval before it touches anything.
  • The proof line: the events socket returns 101, not 403.
Stage 2 · 3–4 weeks

The contract, proven with one app

The host API, a real mount and unmount lifecycle, namespaced storage, and Docs extracted as the first genuine plugin.

  • You see: remove Docs and it leaves the dock, the desktop, spotlight and the agent's tool catalog together. Add it back and it returns. That round trip is the whole thesis.
Stage 3 · 6–8 weeks

Marketplace, the rest of the apps, and the brain

Install and uninstall behind an approval, the remaining apps extracted, the three CDN libraries vendored, and the projection wired end to end.

  • You see: work across three apps, then ask the agent what you were doing. It knows, because it watched.

Where the cost actually sits

Not in the harness integration — that is small and mostly verified already. It sits in stage 2, because the console is 13,504 lines of JavaScript in a single scope with no module boundaries and no tests. "Extract app X" always quietly means "untangle X's free variables from the other 308 functions beside it." The plan is shaped around that, and the honest figure for a full extraction is roughly eight weeks rather than two.
