02

MCP and Agents, in depth

These are the two capabilities you named. Both exist. Both are more capable than the interface admits — and in both cases the gap between what the backend does and what a user can see is the whole problem.

Deep dive A · capability 05 · /tool-mcp

Tools & MCP servers

An MCP server, in this product, is a connector process running inside the Magna cluster that advertises a set of tools the model may call — search a Jira project, read a Drive file, post to a Slack channel. Four are shipped. The catalogue is hard-coded, no server can be added, and today all four advertise zero tools.

The four servers, exactly as a user sees them

Atlassianhttp://atlassian-mcp.magna-system.svc.cluster.local:3000/mcpSign-in required · OAuth0
Google Workspacehttp://google-workspace-mcp.magna-system.svc.cluster.local:8000/mcpSign-in required · OAuth0
Microsoft 365http://ms365-mcp.magna-system.svc.cluster.local:3000/mcpSign-in required · OAuth0
Slackhttp://slack-mcp.magna-system.svc.cluster.local:3000/mcpSign-in required · OAuth0

Every card also shows an enabled blue toggle at the same time as Sign-in required and No tools. Three signals, no meaning: nothing explains what the toggle does when nothing is connected. And nothing anywhere says what connecting Slack would let you do.

How a user meets MCP today

  • They reach /tool-mcp through Connections › Tools & MCPs — or through the composer's sliders icon, where a {} MCP entry appears to do nothing distinct from the rest of the Tools menu.
  • The first thing they read on every card is a Kubernetes service DNS name. It tells a user nothing, tells an attacker something, and makes the product look like an internal admin console.
  • There is no + Add server button anywhere. The entire premise of MCP is bring-your-own; the catalogue is frozen at four.
  • There is no tool list, no permission model per tool, no last-sync, no error log, and no test-connection action.
  • Nothing states which server runs on-prem and which would carry data outside the network — the one question this product exists to answer.

How it should work

  • A connector catalogue, not a server list: logo, name, one plain sentence of value — "Read and create Jira issues, search Confluence" — and a Connect primary action. Grouped Work management · Communication · Storage · CRM · Custom.
  • The endpoint moves behind an admin-only "Technical details" disclosure. Never on the card.
  • A dashed ＋ Add a custom MCP server tile: Name · Server URL · Transport (SSE / HTTP / stdio) · Auth (None / OAuth / Bearer / Header), with Test connection gating the Save button.
  • Discovery is shown, not assumed — and each discovered tool gets a permission default of Always ask / Auto-approve / Blocked before the server is saved.
  • One honest status per card, plus a residency badge stating whether the connector's traffic stays inside the network.

The status a card should be able to show — one value, never three

Not connected→ Connecting…→ Reaching server…→ Discovering tools…→ Connected · 14 tools /Error · view log

The messaging group is an agent-to-agent delegation network. One user's agent can send work to another user's agent, receive a request, reply to it, and enumerate who it can reach — five tools, shipped and working. There is no UI for it anywhere: no contacts page, no inbox of inbound task requests, no outbox of what you have delegated. The etiquette for it is even written down, in two markdown files buried under Profile › Personality (TASK_REQUEST.md, TASK_RESPONSE.md). Building Contacts & delegation — "your agent's network", a contacts list, "Requests to you" and "Requests you sent" with Accept / Decline — turns an invisible backend into the most differentiated demo in the product.
The worked example already exists. The email MCP flow specified separately in BRIEF-V2.md — choose provider, authorise in the provider's own window, opt in to Send mail as you, state where mail is indexed, then read and draft from chat with a real send confirmation — is the pattern every connector on this page should follow. It is not duplicated here.
Deep dive B · capability 06 · /agent

Agents

An agent is a named delegate with its own system prompt, its own model, its own allow-list of skills, MCP servers and built-in tools, and its own autonomy settings. The creation flow is one of the best-built things in the product. It is reached by clicking a nav item called Tasks.

Four nouns for one concept, in four consecutive views

Nav item → "Tasks" Page title → "Tasks" Page subtitle → "Custom roles for delegation" Primary button → "+ New agent" Next screen → "Create subagent"

A user cannot form a mental model from this. Pick one word — Agents — and use it in the nav, the page, the button and the editor. Reserve "task" for scheduled work.

How an agent is created today

Create manually From template Import from JSON Create with AI — describe what you want, an AI drafts the config

All four paths are good, and all four sit behind a button labelled with the wrong noun, on a page whose empty state is "Nothing here yet" in a bare table. Ten well-written templates, an AI-drafted path and a JSON import are invisible until you press it.

The editor — four tabs, and what is in them

TabFields todayProblem
BasicsName · Description · System prompt (pre-filled from template) · Model The model dropdown's default option is the raw code token __inherit__. It should read Same as chat (recommended).
Skills & ToolsRequired skills (18 checkboxes) · Required MCP servers (4, again with raw cluster URLs) · Required built-in tools (10 checkboxes) 32 checkboxes in three flat lists, no search, no grouping, no "select recommended".
AdvancedRestrict tools — "When on, the subagent can only use the tools you select here (instead of inheriting the full tool set)." Right control, wrong noun, buried under a tab called Advanced.
SettingsEnabled · May interrupt the user — "Let this subagent pause mid-task to ask you a clarifying question. Turn off for fully automated subagents." This microcopy is the best in the product. It deserves a better home than a fourth tab.

How an agent runs today — and what is missing

  • There is no test or preview before saving. You write a system prompt, tick 32 boxes, save, and find out later.
  • There is no @mention in the composer — no visible way to invoke a named agent from chat. Invocation goes through the agents skill, implicitly, at the model's discretion.
  • There is no run history, no last-run output, no usage count, no versioning and no duplicate.
  • The peer-delegation tools exist (Send task request / Send task response / List contacts) but nothing in the agent editor mentions them and no surface shows their traffic.
  • Scheduling lives somewhere else entirely — under the same nav label, in two different engines (Heartbeat and Schedules) with two different UIs.

What to build

  • Identity tab: name, one-line purpose, avatar colour, a "How it should behave" field with three insertable example blocks, and a model dropdown that never shows a code token.
  • Access tab: replace 32 checkboxes with four preset cards — Read-only research · Documents & reports · Connected systems · Full access — each listing what it grants in plain words, with a collapsed "Fine-tune permissions" disclosure underneath.
  • Autonomy tab: "May pause to ask you a question", "Restrict to the tools selected above", and a third that does not exist yet — "Requires approval before actions that send, publish or delete."
  • Test tab: a prompt box, a Run button, a live trace of every step and tool call, and a verdict banner — "Used 3 tools · asked 1 question · 8s".
  • An agent list once agents exist: name, purpose, access preset, last run, runs this week, status toggle, and an overflow of Duplicate / Test / Export JSON / Delete.
  • @mention agents in the composer with autocomplete — the missing invocation path.

05

Sequencing

Ordered by what unblocks a seat, then by what needs no design debate, then by what needs a shell, then by what wins the deal.

Now

Launch blockers

The answer surface cannot display its own output. Any technical seat is unusable until these ship.

  • Math renderer. Integral-calculus answers return ~25 lines of literal $\int x^3 , dx$.
  • Diagram renderer. Flowcharts are drawn in box-drawing characters and reflow into garbage at any other width.
  • Code-block chrome — language, filename, wrap, and a copy button.
  • Copy full message. Nothing on an answer copies the whole response.
  • Fix the malformed LaTeX delimiters in the prompt template while you are in there.

Week 1

No debate

Each of these is a default, a string or a deletion. None of them needs a designer in the room.

  • Companion off by default
  • Prompt chips pre-fill instead of send
  • Trace panel collapsed by default
  • Copy button on every answer
  • Fix focus after modal close; bind ⌘K
  • Style the 404 page
  • Remove the Upcoming nav section
  • Remove elon-musk-perspective-en; hide salesforce-uat-api from non-admins
  • Hide *.svc.cluster.local behind an admin disclosure
  • Replace "the pod runs a heartbeat tick" and __inherit__

Weeks 2–6

The shell

The screen people spend 95% of their time on, rebuilt.

  • Permanent conversation sidebar — full titles, date groups
  • Flat default surface, wallpaper opt-in, Appearance cut to four controls
  • Citations with a visible web / internal split
  • Agent template gallery as the empty state, one noun throughout
  • Merge Heartbeat + Schedules into Automations
  • Launchpad home screen replacing the marketing hero

Quarter

Differentiators

What the product is actually sold on.

  • Resolve the residency claim. Highest priority of anything on this page — the Private badge is shown while Usage reports azure/* and bedrock/* routing.
  • Sovereignty guardrail + per-answer residency receipt
  • Context rail — the Agentic Twin surfaced
  • Work / Build / Govern split
  • Canvas entry points + a Create menu
  • API-to-skill wizard as the headline demo
  • Knowledge spaces with permissions
  • Voice surfaces — mic, playback, hands-free
  • Devices pairing flow with explicit folder scope
