Skills, connectors, MCP servers and agents — and how to call them

Six questions, answered in order. No prior knowledge assumed. Every button named here is a button that exists in the prototypes, spelled the same way.

Written for a procurement or delivery lead· Takes about twelve minutes· Nothing here requires an IT ticket

If you only have thirty seconds

  1. 1Add a skill Connections → Skills → flip its toggle to On. For a new one: + Add skill → From a template.
  2. 2Connect an MCP server Connections → Tools & MCP → Connect Magna Mail → four steps: Choose, Configure, Permissions, Done.
  3. 3Add an agent Agents → Create agent → pick a template, name it, pick its access and its trigger, test it, save.
  4. 4Add a connector Connections → Tools & MCP → pick your system → Connect Jira. Reading switches on. Writing stays off until you tick it.
  5. 5Send a mail, raise a Jira issue Just ask. Magna drafts it into a box you can edit, then shows you one confirmation naming exactly what will go out. It never sends on its own.
  6. 6Call any of them Type / in the message box and pick from the list — or just ask in plain English and let Magna choose.
00

Three things, three different jobs

Almost every confusion about this product comes from these three words being used interchangeably. They are not the same, and the difference is simple.

One sentence each

  • A skill is a saved instruction. A repeatable job Magna already knows how to do — "write the weekly HSE digest" — written down once so it comes out the same way every time.
  • An MCP server is a connection to one of your systems. It gives Magna tools: "search mail", "look up a purchase order", "read a Jira issue".
  • An agent is a worker. A named role with its own model, its own tools and a trigger — and it is the only one of the three that can run on a schedule, without you.
MCP stands for Model Context Protocol. Ignore the words. It is a plug shape — an agreed way for one of your systems to offer its functions to an AI, so you connect SAP or your mail once instead of building an integration for every product you buy. A tool is one single thing Magna can do inside that system.

You will also see the word connector. It is the same object described from your side — the link to one of your systems — and it is what the catalogue calls them. Section 03 untangles the two words properly and lists all ten.

How they fit together

Side by side

01

How do I add a skill?

Most of the time, "adding" a skill means turning on one that already exists. That is one click. The longer routes are for skills nobody has written yet.

The one-click route — from the catalogue

  1. Open Connections, then the Skills tab.

    You get a grid of cards, not a checkbox list. Each card is written for you, not for the model: a plain-language name, the internal id in small grey type underneath, one sentence of what it does, and a real example prompt.

  2. Narrow it down.

    Search matches the name, the description and the id. The filters are the ones that matter: category — Reporting, Engineering, Procurement, HSE, Admin — and Ready to use versus Needs a connection.

  3. Press Try it before you commit.

    This puts the card's example prompt into the message box. It drafts — it does not send. Read it, change it if you like, and press ↵ when you are happy. This is how you judge a skill, instead of guessing from its name.

  4. Flip the toggle to On.

    That is the whole thing. The skill is now available in chat and in the / menu, and any agent you create can be given it.

When a card says "Needs Company Knowledge"

This is not an error and the skill is not broken. It is telling you that the skill leans on a connection your workspace does not have yet — in this case the document index, Company Knowledge. Nothing about the skill needs fixing.

What to do. Press Connect on the chip. It drops you into the connect stepper from section 02, already pointed at the right system. Finish those four steps, come back to the Skills tab, and the amber chip has become a green Ready to use with a normal toggle. Nothing you did in the Skills tab is lost.
The name in the chip is always the thing that is missing. Needs Magna Mail means connect your mail. Needs SAP purchase orders means connect SAP. If the chip names a system only your admin can reach, the button reads Request access instead, and pressing it sends the request rather than opening a form you cannot complete.

The other two routes — + Add skill

If nothing in the catalogue does what you need, + Add skill offers three cards. The first is the catalogue you have just seen. The other two:

  1. From a template — describe it in plain language.

    A short guided flow, in the same four steps as everything else.

    • Name it the way your team would say it out loud — "Weekly supplier scorecard". The internal id is generated for you: weekly-supplier-scorecard. You never type an id.
    • Say what it should do, in a sentence or two of ordinary English. "Score every active supplier on delivery, quality and prequalification, and rank them."
    • Pick which connections it may use. Only the ones already connected are offered.
    • Pick a trigger — on request, on a schedule, or when an agent calls it.

    A live preview of the finished card updates as you type, so you can see exactly what your colleagues will see. Press Create skill when the preview reads well.

  2. Import a skill definition.

    For a skill someone has written as a file. Paste it in and press Validate. It is checked before it goes anywhere near your workspace.

What this replaces today Skills currently live behind Tools → Skills 18/18 as an 18-item checkbox list of internal names — heartbeat, magna-api-skill-generator, jira-ticket-definer — all switched on by default, with descriptions written for the model rather than for you and cut off mid-sentence. One of the eighteen ships to end users with the words failed to parse SKILL… as its description.

02

How do I connect an MCP server?

Four steps, always the same four, whichever system you are connecting. The worked example here is Magna Mail, because mail is the one everybody wants first. Section 03 is the list of every system you can point these four steps at, and section 04 takes mail and Jira all the way through to sending.

Step by step

  1. Open Connections, then the Tools & MCP tab.

    One sentence at the top of that view explains what an MCP server is, so you never have to remember. Each server is a card: its name, what it gives you in plain words, the tools it exposes, where it runs, and one honest status — Not connected, Connected, or Error with the last sync time.

  2. Find Magna Mail and press Connect Magna Mail.

    The stepper opens. You can leave at any point before step 4 — press Escape or the close button. Nothing is committed until the last step.

  3. Step 1 — Choose your provider.

    Four options, and the residency consequence is stated on each one rather than buried in a policy document.

  1. Step 2 — Configure the account.

    Your email address and the display name to send under. There is no password field, and there should never be one. Press Authorise in provider → and your mail provider's own sign-in window opens. You approve it there, in the window you already recognise. MagnaVERSE never sees your password.

  2. Step 3 — Choose what it may do.

    Four plain-English checkboxes, not permission codes. Read mail is on. Send mail as you is off — you have to tick it deliberately. Read contacts and Read calendar are your choice. The panel above is exactly this step.

    You can change all of this later without disconnecting: the same card gets a Permissions action once connected.

  3. Step 4 — Done, and it tells you how to use it.

    The last step is not a "Success!" banner. It lists what got connected, which permissions you granted, the four tool names, the / commands they map to, and a Try it button that puts a working example in the message box.

  4. Press Test connection.

    On the card, any time. It runs a real check and reports a real result — which tools responded, how long they took, and a readable error if one did not. This is how you tell a working server from a broken one without opening a ticket.

What visibly changes after you connect

Connecting something is pointless if nothing happens. The moment step 4 completes, four things change that you can see:
  • The mail tools appear in the / menu. Before, they were greyed out with a Connect … label.
  • The connection count in the sidebar goes up by one.
  • Skills that said Needs Magna Mail now have a working toggle, and the starter prompts on the home screen change.
  • "Connect your mail" ticks itself off the Finish setting up checklist.
Disconnecting really disconnects. The same card has a Disconnect action. It reverts the status, removes the tools from the / menu, and re-greys anything that depended on it. Nothing is left half-connected.

Connecting something that is not in the catalogue

+ Add server gives you the same three routes as skills:

  • From the catalogue — pick a server above and follow the four steps. This is the usual way.
  • From a template — name it, give it a server address and a transport, choose the auth. Your admin gives you the address; an address inside your network keeps the connector on-prem. It is tested before it saves.
  • Import a config — paste an MCP config file. It is validated the same way a skill is, with the same readable error.
The full version of that middle route — every field, both transports, the visible handshake, and the JSON a developer would actually write, with a copy button — is in section 03.
What this replaces today Today there are four hard-coded MCP servers and no way at all to add a fifth — no + Add server button exists anywhere. The main text on each card is a raw Kubernetes hostname such as ms365-mcp.magna-system.svc.cluster.local:3000, and each card shows an enabled blue toggle, Sign-in required and No tools at the same time. Nothing explains what connecting one would let you do, and there is no way to tell a working server from a broken one.

03

How do I add a connector?

A connector is the link between MagnaVERSE and one of your business systems — your mail, your Jira, your SAP. Connect one and Magna gains a small set of new abilities inside that system. Ten are ready in the catalogue. Anything else, a developer adds.

A connector and an MCP server — what the difference actually is

These two words get used for the same thing, which is why they confuse people. Read the chain below left to right and the difference stops mattering.

Built in, or built by you. Ten connectors ship in the catalogue and take about two minutes each — you press Connect and follow the four steps. Anything not on that list is added once by a developer as a custom MCP server (further down this section). After that it behaves exactly like a catalogue one: same card, same four steps, same permissions.

What one connector looks like

Every card in the catalogue is laid out the same way. The tools are listed in plain language, and each one is marked read or write before you connect anything — so you can see the consequences while you are still deciding.

A connector you have not connected still tells you what it would give you. The card above is a card for a system nobody in your workspace has set up yet. It still lists every tool, still marks read and write, and still names where it runs. You never have to connect something to find out what it does.

The whole catalogue

Ten systems, and everything each one can do. The reads column is what turns on automatically. The writes column is what stays off until you tick it — and every one of those, when it eventually runs, stops and shows you a confirmation first.

Reading a connector's status

One status per card, and it means one thing. There is never a green toggle sitting next to the words "no tools".

Connecting one — the same four steps, every time

Section 02 walked these four steps with Magna Mail. Here they are again with Jira, because the point is that they never change: Choose → Configure → Permissions → Done.

  1. Step 1 — Choose the system, then the variant.

    Pick Jira from the catalogue, then pick which Jira. This is the choice that decides where your data goes, so the consequence is written on each option, not in a policy document.

    • Jira Data Center — your own installation, inside the building. on-prem · 0 bytes leave your network
    • Jira Cloud — Atlassian's servers. Issue text is fetched from their region on every request. leaves your network

    Whichever you pick, you get the same ten tools. The only thing that changes is the residency chip, and it is shown on every answer that used this connector afterwards.

  2. Step 2 — Configure the account.

    Your Jira site address and the account Magna should act as. There is no password field, and there never will be one. Press Authorise in Atlassian → and Atlassian's own sign-in window opens. You approve it there, in the window you already recognise, and it hands back a token. MagnaVERSE never sees your password.

    If your admin has already set the connector up centrally, this step is one line — "Using the workspace connection your admin configured" — and you go straight to step 3.

  3. Step 3 — Grant the scopes.

    Plain-English checkboxes, never permission codes. Reading is ticked because nothing works without it. Every write is unticked, and stays unticked unless you tick it yourself. The panel below is exactly this step.

  4. Step 4 — Done, and it tells you how to use it.

    Not a "Success!" banner. It lists the account, the scopes you granted, the ten tool names, the / commands they map to, and a Try it button that puts a working example straight into the message box.

What visibly changes the moment you press Connect

Connecting something is pointless if nothing happens. Five things change, and you can see all five without leaving the screen.

The five visible changes.
  • The Jira tools appear in the / menu. Before, they were greyed with a Connect Jira label.
  • The connection count in the sidebar goes up by one, and the card now reads Connected · 10 tools.
  • Skills that said Needs Jira get a working toggle. jira-ticket-definer becomes usable.
  • The starter prompts on the home screen change to ones that use Jira.
  • Agent creation now offers the Jira tools in Fine-tune permissions.
Disconnecting really disconnects. Disconnect on the card reverts the status, removes the tools from the / menu, re-greys anything that depended on it, and drops the stored token. Nothing is left half-connected.

The rules that apply to every connector, without exception

  • Writes are off by default. Reading turns on when you connect. Anything that sends, creates, changes or deletes is unticked, and needs a deliberate tick in Permissions.
  • The first time a tool runs in a thread, Magna asks. An inline approval prompt names the exact tool, says whether it reads or writes, and says where it runs. Four answers: Allow once, Allow for this thread, Always allow, Don't allow.
  • A write action always shows a confirmation naming exactly what will change. Not "Magna wants to act" — the actual recipient, the actual subject, the actual issue summary and assignee. You can edit it, cancel it, or confirm it.
  • Magna can never see more than you can. A connector acts as your account. A Jira project you cannot open, Magna cannot open either.
  • Everything a write tool does is logged. Time, tool, what changed, and which conversation asked for it — in the audit trail, whether you did it in chat or an agent did it at 06:00.
Where to revoke. Three places, and they do different jobs. Permissions on the connector's card unticks a scope — the tool disappears from / and stays gone. Settings → Permissions holds the Exceptions table, where every Always allow you ever pressed is a row with a Remove action; removing it just means you get asked again. Disconnect on the card removes the whole connector. Section 06 covers the three permission tiers in full.

Adding a connector that is not in the catalogue

If the system you need is not one of the ten, someone with developer access wires it up once as a custom MCP server, through + Add server → Connect your own server. This is the part of the product you would hand to your integration team; the rest of this page needs nobody technical.

The first question is how the server runs, because every field after it depends on the answer.

  1. Identity.

    A display name your colleagues will read, one line describing what it gives them, an icon colour, and which workspace it belongs to. This is what turns a hostname into a card.

  2. Secrets.

    Environment variables and tokens as key/value rows you can add and remove. Values are masked with a reveal toggle. They live in the workspace secret store and are never sent to the model.

  3. Test connection — a visible handshake.

    Not a spinner and a tick. You watch it happen, and if it fails you get told what to check.

  1. Permissions.

    The discovered tools, each with a plain-language label and a toggle. Read-only tools are on. Anything that writes, sends or deletes is off, and has to be ticked one at a time — the same rule as every catalogue connector.

  2. Done.

    The server appears in the list as a normal card. Its tools appear in /. The connection count increments. From this point on, nobody using it needs to know it was custom.

The config a developer would actually write

On the last step, and on every server's detail view, a Config disclosure shows the equivalent JSON with a copy button. If you are handing this to your integration team, this is the part to send them.

Local process — stdio 
{
  "mcpServers": {
    "magna-jira": {
      "command": "npx",
      "args": ["-y", "@magna/jira-mcp"],
      "env": {
        "JIRA_BASE_URL": "https://magna.atlassian.net",
        "JIRA_TOKEN": "••••••"
      }
    }
  }
}
Remote — HTTP / SSE 
{
  "mcpServers": {
    "magna-jira": {
      "url": "https://mcp.magna.internal/jira",
      "transport": "http",
      "headers": {
        "Authorization": "Bearer ••••••"
      }
    }
  }
}

The dots are not a placeholder to fill in here. Secrets are entered in the Secrets step, stored in the workspace secret store, and masked everywhere they are displayed — including in this config view. Never paste a live token into a document, a chat message, or a prototype.
What this replaces today Today there are four hard-coded servers and no way to add a fifth. The main text on every card is a raw Kubernetes hostname — ms365-mcp.magna-system.svc.cluster.local:3000 — which tells a user nothing and an attacker something. Each card shows an enabled blue toggle, Sign-in required and No tools at the same time: three signals, no meaning. There is no way at all to tell a working server from a broken one — no test, no tool count, no last-sync time, no error text. Nothing anywhere says what connecting any of them would let you do. And in the skills list next door, an entry called salesforce-uat-api carries a UAT sandbox endpoint — magnaai--uat.sandbox.my.salesforce.com — as its description, in a production screen.

04

Mail and Jira, end to end

The two connectors people ask for first — mail because everyone has one, Jira because that is where the work is tracked. Then the thing this whole page has been building to: one sentence that uses both.

Mail — four variants, and what each means for your data

This is step 1 of the connect flow, and it is the only decision in it that you cannot change later without disconnecting. So it is worth thirty seconds.

Changing your mind later. Scopes you can change any time from Permissions on the card — turn Send mail as you on or off without touching anything else. The variant you cannot: switching from Microsoft 365 to Magna Mail means Disconnect and connect again, because it is a different mailbox and a different residency answer.

Reading and searching your inbox from chat

Once mail is connected you do not go to a mail screen. You ask. There is a Mail view if you want one, but the point of the connector is that your inbox becomes something you can ask questions about.

What reading costs you: nothing. Searching, opening a message, summarising a thread and downloading an attachment are all read tools. They are on from the moment you connect, they never ask again after the first approval, and on Magna Mail none of it leaves Riyadh DC-1.

Drafting a reply — it drafts, it does not send

Say "reply to Al-Rashid and ask for a revised delivery schedule" and a composer opens inside the conversation with the reply already written in it. Every field is editable. Nothing has left your outbox.

There is no path where mail leaves without you pressing something. Not from chat, not from a skill, not from an agent at 06:00. The most an agent can do unattended is leave a draft waiting for you — and the digest tells you it is there.

The send confirmation

Press Review and send and you get one last screen. It is not a "are you sure?" — it is the actual message, one more time, with the things people get wrong pulled out and made obvious: who it is going to, which account it is going out as, and what is attached.

After you press Send. A success line appears in the conversation with the time and a View in Sent link, the message appears in your Sent list, and one row is written to the audit trail: 10:41 · magna-mail.send · 1 recipient external · from this conversation. Nothing about the send is invisible.

If Send mail as you was never granted

You still get the draft, and you still get the confirmation. What you do not get is a working Send button — because the scope you skipped in step 3 of the connect flow is the one that permits it. The screen tells you exactly which tick box, and takes you to it.

If the thread is on the Public tier

Every conversation carries a tier. Private means everything stays on the Magna cluster in Riyadh. Public means the conversation may use a model outside your network — which is fine for general drafting, and not fine when the draft quotes your own documents. Sending from a Public thread that quotes internal material trips a guardrail before anything goes out.

Jira — reading first

The four read tools are on from the moment you connect. You never type JQL — Jira's query language — unless you want to. Ask in English and Magna writes the query, then shows you the query it wrote underneath the answer.

Jira — the six things it can write

Each of these is off until you tick its scope, and each one shows you the filled-in change before it happens.

  • Create an issue — you see the whole issue drafted: project, type, summary, description, priority, assignee, labels. Nothing is invented silently; anything Magna guessed is marked.
  • Comment on an issue — you see the exact comment text and who gets notified by it.
  • Change an issue's status — you see the move written out: RDC2-418 · In progress → Blocked, and any field the transition forces you to fill in.
  • Assign an issue — you see the person's full name, not an account id, and the fact that they will be emailed.
  • Link two issues — you see both keys and the link type: RDC2-419 blocks RDC2-418.
  • Log work — you see the hours, the date and the issue. If your team bills from Jira, this is the one to leave off.

Two connectors, one instruction

This is the payoff, and it is the example built into all six prototypes. One sentence, two systems, one confirmation.

  1. Magna asks permission — once, for both.

    One approval prompt, naming both write tools rather than interrupting you twice. magna-mail.send and magna-jira.create-issue, each with what it will do and where it runs. Allowing this does not send anything — it lets Magna prepare both drafts.

  2. It reads before it writes.

    The reasoning line names each read as it happens: the Al-Rashid thread from magna-mail.search, the C2 milestone dates from p6-schedule, and the open issues on the RDC2 board from magna-jira.search-issues. Reads never ask.

  3. You get an editable mail draft.

    The composer from earlier in this section, with the reply already written and the Cc explained. Edit anything.

  4. And a drafted Jira issue underneath it.

    The issue card from earlier in this section — project, type, summary, description, priority, assignee, labels — with the two inferred fields marked. Edit anything.

  5. Then one confirmation, covering both.

    Not two prompts in a row. One panel listing both actions in the order they will run, with a single Confirm both. You can still peel one off and cancel it.

Press Confirm both and both complete in a couple of seconds. The conversation gets a short result — "Sent to Khalid Al-Rashid. Created RDC2-419 and assigned it to Faisal." — with RDC2-419 as a working link. And two rows land in the audit trail.

The same sentence works from an agent. Give Mail Triage the mail and Jira connectors and this becomes something that runs at 07:00. The difference is that an agent stops at the confirmation and waits: you get one notification saying two actions are ready, and pressing Confirm both from the notification does exactly what pressing it here does. Section 05 covers agents.
What this replaces today Today none of this exists. There is no mail connector — the closest thing is a built-in tool called Email file whose entire description is "Send a workspace file or artifact as an email attachment", with no account behind it, no composer, no confirmation and no way to read anything. Jira is not a connector either; it appears as a skill called jira-ticket-definer with its description cut off mid-sentence, and an Atlassian MCP card next door that shows Sign-in required and No tools at once. Nothing in the product distinguishes an action that reads from an action that sends, and the one switch that would have made it ask — Trust built-in tools and skills — ships on.

05

How do I add an agent?

An agent is a name, a model, a set of tools and a trigger — nothing more. If you can describe a colleague's job in two lines, you can make an agent.

Step by step

  1. Open Agents and press Create agent.

    You land on a gallery of starting points, not an empty form: Procurement Analyst, Contract Clause Reviewer, HSE Incident Reporter, Schedule Slip Analyst, Vendor Risk Screener, Mail Triage. Pick the closest one — you can edit every field before saving, and nothing is created until you do.

    If none of them fits, describe what you want in plain English and let MagnaVERSE draft the configuration. The draft is shown to you before anything is saved.

  2. Name it, and say what it is for in one line.

    "PO Slippage Watch — compare released purchase orders against the live P6 snapshot and raise anything slipping." That line is what your colleagues will read, so write it for them.

  3. Pick the model, or don't.

    The default option reads Same as chat (recommended). Leave it unless you have a reason. You will never see a code token like __inherit__ in this dropdown.

  4. Pick what it may use.

    Four access presets, each spelling out what it grants in ordinary words:

    • Read-only research — look things up, never change anything.
    • Documents & reports — the above, plus producing files and drafts.
    • Connected systems — the above, plus reading from SAP, P6, Jira, mail.
    • Full access — everything you personally have. Use sparingly.

    If you want to be precise, open Fine-tune permissions underneath and pick individual tools from a searchable, grouped list. Most people never open it.

  5. Pick a trigger. This is the decision that matters.
    • On request — it only runs when you press Run, or @mention it in chat. Start here.
    • Scheduled — it runs on a clock. You get a plain-English preview of the schedule as you set it: "every weekday at 06:00". No cron syntax unless you want it.
    • Called by another agent — it does nothing on its own, and exists so a bigger agent can hand it a piece of work.
  6. Test it before you save.

    Type a sample prompt into the test panel and press Run. You see a live trace — every step and every tool call as it happens — and a verdict line at the end: "Used 3 tools · asked 1 question · 8s". If the trace shows it reaching for something you did not intend, fix the access preset and run it again. This costs you thirty seconds and saves you a surprise at 06:00.

  7. Save. Then let it run.

    It appears in the Agents table with its model, its access preset, its trigger, its last run and its run count. The toggle on the row is the on/off switch — turning it off stops the schedule without deleting anything.

How to check what it actually did

Press Open on the agent's row. The run history is the middle of that panel: one line per run, with the time, the result in a readable sentence, how many tools it used and how long it took. Click a run to see the full output it produced and the tools it called, in order.

Two rules that always hold, whatever you configure. An agent can never use a tool you have not granted it. And anything that sends, publishes or deletes still stops and asks you — an agent running at 06:00 will draft the email and wait, it will not send it while you are asleep unless you granted that explicitly.
What this replaces today Today the same concept has four names in four consecutive screens: the nav says Tasks, the subtitle says "custom roles for delegation", the button says + New agent and the next screen is titled Create subagent. Access is three flat checkbox lists — 18 skills plus 4 servers plus 10 tools, 32 boxes with no search and no grouping — the model dropdown offers __inherit__, and the empty state is a blank table that hides ten perfectly good templates behind a button labelled with the wrong noun.

06

How do I call them?

This is the question that matters, and the answer is short: type a slash, or just ask. Everything else on this page exists to make those two things work.

1 · Type / in the message box

The menu opens the moment you press the key. It lists every skill that is on and every tool from every connected MCP server, each with a one-line description. Keep typing to filter — it matches names and descriptions, so /po finds both the purchase-order tool and the PO variance skill.

2 · Or just ask, in your own words

You do not have to remember any of those names. Type "Summarise this week's HSE incidents for the steering pack" and Magna picks the skill itself. It then shows you which one it used, in the reasoning line above the answer — so you learn the names by seeing them, rather than by memorising them.

3 · ⌘K for everything else

⌘K on a Mac, CtrlK on Windows. This is the whole product in one box: views, conversations, documents, agents, and actions. Type three letters of what you want.

4 · Running an agent on demand

  • Press Run on its row in the Agents table.
  • Or press Open and then Run now inside it, if you want to watch the trace.
  • Or @mention it in the message box — type @ and its name autocompletes — to hand it a job mid-conversation.
  • Or ⌘K → "Run" → its name.

5 · How a scheduled agent delivers its result

You do not go looking for it. When a scheduled agent finishes, the run appears in Automations with its result written in a sentence, and the output is delivered wherever you told it to go: a notification, a new message in your chat, or a post to a channel. Nothing is buried in a log file you have to find.

If a scheduled run fails, you get told, once, with what stopped it and a Run now to retry. Silent failure is the thing this replaces.

The first time it touches a real system

Magna stops and asks. The prompt appears inline in the conversation, not as a modal you dismiss reflexively. It names the exact tool, says whether it is read-only, and says where it runs.

What each button means

  • Allow once — just this one call. You will be asked again next time.
  • Allow for this thread — for the rest of this conversation. A new conversation asks again.
  • Always allow — pins a rule. This tool runs without asking from now on, and the rule appears in Settings → Permissions.
  • Don't allow — it does not run, and Magna answers with whatever it can do without that tool.

Granting and revoking later

Settings → Permissions holds three tiers, and they behave differently on purpose:

To revoke: find the rule in the Exceptions table and press Remove. It reverts to the tier default, which means you will simply be asked again the next time. To take a whole system away, use Disconnect on its card in Tools & MCP, or untick the scope in Permissions — for example turning off Send mail as you while keeping Read mail.
What this replaces today Today a single switch called Trust built-in tools and skills is on by default, which means the approval prompt — the one component that teaches people how permissions work — never appears at all. The three override lists underneath are permanently empty, and the help text's illustrative example is github/delete_repo.py. There is no risk tiering: "send an email" and "delete a repository" are treated identically.

Quick reference

Print this bit, or keep the tab open. It is the whole page in one card.

The six answers
Add a skill
Connections → Skills → toggle it On. Press Try it first to see what it does. For a new one: + Add skill → From a template → name it, describe it, pick its connections and its trigger.
Connect an MCP server
Connections → Tools & MCP → Connect Magna Mail → Choose the provider, Configure the account in the provider's own window, tick the Permissions you want, Done. Then Test connection.
Add a connector
Connections → Tools & MCP → pick the system → Connect Jira → the same four steps. Reading turns on. Writing stays off until you tick it in Permissions. Not in the catalogue? + Add server → Connect your own server — a developer job, once.
Send a mail or raise a Jira issue
Ask in plain English — "reply to Al-Rashid and raise a Jira issue for the delay". Magna drafts both into boxes you can edit, then shows one confirmation naming the recipient, the subject, the project and the assignee. Confirm both is the only thing that makes anything happen.
Add an agent
Agents → Create agent → pick a template → name it, choose an access preset, choose a trigger (on request / scheduled / called by another agent), press Run in the test panel, save.
Call any of them
Type / in the message box and pick from the list, or just ask in plain English. Agents also run from Run on their row, from @mention, or on their schedule.
KeyWhat it does
/Opens the list of every skill and every connected tool, in the message box.
⌘K or CtrlK The command palette — every view, conversation, document, agent and action.
↵Sends your message. In a menu, inserts the highlighted item.
⇧↵New line inside the message box, without sending.
↑↓Move through the / menu or the palette.
EscCloses any menu, sheet or stepper. Your cursor goes back to the message box.
@Mentions an agent, to hand it a job mid-conversation.
If you are setting up from scratch, do it in this order. Connect your mail first — it unlocks the most. Then turn on one skill and press Try it. Then add a knowledge source so answers cite your own documents. Then create one agent on a schedule. That is exactly the order of the Finish setting up checklist in the sidebar, and each row ticks itself when you genuinely finish it.
