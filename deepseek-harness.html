01

What an agent harness is, in plain language

Start here. If you already know the difference between a model API and an agent runtime, skip to section 3.

A model API is a single question and a single answer

When you call a model over HTTP, you send some text and you get some text back. The model has no memory of the call afterwards. It cannot open a file. It cannot run a command. It cannot ask you for permission. It cannot continue tomorrow from where it stopped today. It is a function: text in, text out.

That is enough for a chatbot. It is not enough for anything in Console.

An agent is a loop around that call

Take one of Console’s own examples. The PO Slippage Watch agent checks every open purchase order against the live Primavera P6 baseline. To do that, something has to:

  • read the P6 snapshot — that is a tool call, not text generation;
  • read the SAP purchase orders — another tool call, to a different system;
  • notice that the answer needs a third lookup, and call the model again with what it just learned;
  • stop before it writes anything, and ask a human;
  • write down every step, so that tomorrow someone can ask “why did it say that?” and get a real answer;
  • survive a browser refresh, a laptop closing, and a server restart.

The model does none of that. The model only decides what it wants to do next. Everything else — running the tool, enforcing the permission, keeping the log, resuming the work — is done by the program that wraps the model.

The definition

An agent harness is that wrapping program. It owns the loop: call the model, read what it asked for, run the tools, feed the results back, decide whether to stop, and record all of it. Claude Code is a harness. Codex CLI is a harness. dsh is a harness. The model is the engine; the harness is the whole car.

Why you do not want to write one yourself

Every team that starts down this road writes the same five thousand lines twice. Streaming and re-assembling partial responses. Running several tools at once without them corrupting each other. Cancelling a run half-way through. Compacting a conversation that outgrew the context window. Retrying only the failures that are worth retrying. Making the transcript replayable, so that the audit trail and the screen agree.

None of that is your product. All of it is required before your product works. A harness is the part you should adopt rather than build — provided you can still control the parts that are your product: which model, which network, which data, and who says yes.

That last sentence is the whole reason dsh is worth this page.

03

The one idea that makes dsh different: everything is a plugin

This is the section that decides whether dsh is interesting to Magna. Everything else follows from it.

The usual shape, and why it hurts

Most agent frameworks have a core and then extensions. The core owns the loop, the model call, the tool runner and the log. Extensions are allowed to attach at the few places the core author thought of. When you need something the core author did not think of — say, “refuse any tool whose data would leave Saudi Arabia” — you have three bad options: submit a patch upstream and wait, fork the project and maintain it forever, or monkey-patch it at runtime and pray.

dsh does not have that shape. Its architecture document says it directly:

Verified — architecture.md

“Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself, so every part is replaceable from configuration. There is no privileged core to patch: you extend dsh by mounting a plugin beside the others, and registrations are effects that unwind when their plugin unloads.”

Read that once more with Magna’s constraints in mind. The model adapter is a plugin, so the model is swappable — that is Console’s four on-prem models. The filesystem provider is a plugin, so where files live is swappable. The sandbox is a plugin, so where commands run is swappable. Nobody had to anticipate Saudi data residency for it to be expressible.

Cordis in five ideas

Cordis is the plugin framework underneath dsh. Its primer states five ideas. Here they are, each followed by what it means for you.

Idea 1

A plugin is an object that implements Service

The rule. A plugin can simply be a function with optional inject and apply(ctx) fields, or a Service subclass whose lifecycle Cordis mounts into the current context.

What it means. A plugin is an ordinary TypeScript file. There is no base class you must inherit, no manifest ceremony. A Magna policy is one file with an apply function.

Idea 2

A context is a repository of services

The rule. A service claims a stable key such as ctx.tools, ctx.llm or ctx.sessions. Other plugins find services by key, instead of importing a concrete implementation.

What it means. The Bash tool does not import “the local filesystem”. It asks for ctx.fs. If you register a different ctx.fs, Bash silently starts working against your filesystem. Nobody edits Bash.

Idea 3

Declare dependencies with inject

The rule. A plugin that names the services it requires waits until those services exist. Load order is expressed through service requirements rather than manual boot sequencing.

What it means. You never write startup ordering code. export const inject = ['tools', 'approval'] and your plugin activates at the right moment, and deactivates cleanly if those services go away.

Idea 4

Typed events for communication

The rule. Services declare event names through TypeScript declaration merging, then dispatch them as emit, waterfall, parallel or serial — depending on whether listeners observe, wrap, fan out, or run in order.

What it means. The extension points are typed, named and catalogued. Your compiler tells you when one changes — which matters a great deal in a developer preview.

Idea 5

Registrations are reversible effects

The rule. Prompt sections, tool schemas, adapters, providers and listeners are installed through ctx.effect() or ctx.on(), so reload and teardown unwind them predictably. Every registration returns its exact disposer.

What it means. This is the quiet one that matters most. Turning a capability off is a real operation, not a hope. A tenant that loses its licence, a connector that must be cut at 02:00, a residency mode that must remove every network tool — those become one disposer call, not a restart.

How a running dsh is composed: profiles, bundles, patches

A running dsh is a plugin tree that is assembled at start-up from ordered layers. Three words carry the whole system, and the architecture document defines each of them:

  • A profile is a named composition stored in the Harness home. It lists the bundles it stacks, holds any out-of-tree plugins it installs, and keeps the user’s own cordis.patch.yml. web and headless ship as templates.
  • A bundle is a distribution format for configuration rows and the code they mount, so whatever it inserts stays patchable by the layers above it.
  • A patch targets a row by its id and either replaces that row’s whole configuration, or inserts new rows.

Layers apply to an empty entry list in a fixed order: each bundle in the profile’s listed order, then the profile’s cordis.patch.yml, then the home-level one, then any --patch overlay given on the command line.

Why this is a big deal for a sovereign product

Magna’s requirements are not features you add. They are substitutions you make: this model instead of that one, this filesystem instead of that one, this sandbox instead of that one, this permission-asker instead of that one.

In a framework with a privileged core, a substitution means a fork — and a fork means you inherit the maintenance of a project you did not write. In dsh, a substitution is a configuration row. You keep receiving upstream releases while running a product that shares almost no code path with the default one. That is the difference between adopting a library and adopting a liability.

04

The turn flow — what actually happens when someone presses Enter

This is the sequence Console’s chat, agents and automations would all run through. Learn two words first.

Verified — architecture.md Step and turn

A step is one model request plus the tools it calls.
A turn is zero or more steps. It opens before its first input is claimed, and closes once nothing is owed.

A simple question — “what is our exposure on RYD-M3?” — may be one turn of one step. A real Console task is one turn of many steps: the model asks for the P6 snapshot (step 1), reads it and asks for the SAP purchase orders (step 2), reads those and writes the answer (step 3). One turn. Three model requests. Six tool calls.

Why the distinction matters to you: the turn is the unit a human recognises (“I asked, it answered”), and the step is the unit that costs money and can be intercepted. Console’s cost meter counts steps. Console’s approval bar interrupts inside a step. A turn that was rejected before its first step still gets recorded, so the log shows the attempt.

The session log is the single source of truth

One sentence from the architecture document is worth memorising, because it is the reason this design can be audited:

Verified — architecture.md

“Model-visible means logged.” Anything that reaches a model request must be reconstructable from the log, and a runtime invariant asserts it.

The conversation the model sees is not a variable in memory. It is projected from the append-only log by a function the document calls deriveMessages(). Fork, resume, transcripts, telemetry and persistence all derive from that same stream.

For Magna this is the difference between a demo and a regulated system. If a claim was made, the exact bytes that produced it are on disk, in order, with the tool calls that fed them. Console already promises “Brain node ids behind every claim”. This is the runtime that can actually keep that promise, because there is no other place for context to hide.

05

Dispatch modes, and the waterfall — the mechanism that lets Magna insert policy

Four ways an event can be delivered. Only one of them can say “no”, and that one is the one you will use most.

In Cordis, every event declares how it is dispatched. The mode is part of the event’s public contract — it is not something a listener chooses. The primer gives this table:

Cordis dispatch modes
ModeAwaited?Dispatch orderHas a return value?In plain words
emitNolisteners observe in registration orderNoTell everyone. Nobody can change anything or block. Used for notifications.
waterfallNolisteners observe in registration orderYesPass it along a chain. Each listener may change the result, or stop the chain. This is where policy lives.
parallelYesall listeners observe in parallelNoEveryone at once, and wait for all of them.
serialYeslisteners observe in registration orderYesOne after another, awaited, and a value comes back.

What a waterfall actually is

Verified — cordis-primer.md

ctx.waterfall is around-middleware. A listener receives (...args, next). Call next() to delegate the possibly-wrapped result to the next service; return without next() to short-circuit. Values propagate through next()’s return value.

The primer adds the design rule: “For single-decision events, short-circuiting is the design. A policy listener can return without next() when it owns the decision, while a listener that only annotates or observes must delegate.”

If you have used Express or Koa middleware, you already know this shape. If you have not, here is the whole idea in six lines:

the waterfall shape — two behaviours, one function
ctx.on('tools/pre-execute', async (exec, next) => {

  // 1 — NOT MY DECISION: delegate. Whatever the rest of the chain
  //     decides becomes the answer. This is the polite default.
  if (!isWrite(exec)) return next()

  // 2 — MY DECISION: return WITHOUT calling next().
  //     The chain stops here. Nothing downstream can undo it.
  return { kind: 'deny', reason: 'Rejected in the Console approval bar.' }
})
Why this is the answer to “how do we add our rules without forking?”

Magna’s rules are almost all decisions about someone else’s action. “This write needs a human.” “This tool would leave the country, so it does not run.” “This agent is at autonomy level 2, so it may read but not send.”

A waterfall listener is exactly that: a function that sits in front of an action it did not write, and either steps aside or refuses. You do not modify the Bash tool to add an approval. You do not modify the SAP connector to add residency. You register one listener, and it applies to every tool, including tools that did not exist when you wrote the rule — including tools a customer installs from the Marketplace tomorrow.

One more detail from the primer that you will need: { prepend: true } puts your listener before ordinary registrations. Use it only when your rule must genuinely run first.

06

The tool pipeline — where Console’s approval bar plugs in

Every tool call, from every agent, in every session, goes through this one path. That is what makes a single rule enforceable everywhere.

Three properties of this pipeline you should hold on to

Property 1

Approval fails closed

The approval outcome type is closed: allowed-once, rejected, cancelled, unavailable. Only allowed-once proceeds. A missing, non-owning, throwing or non-conforming answerer becomes unavailable — which denies.

Console’s promise is “nothing irreversible happens without your yes”. Here, silence is a no. That is the correct default and it is the shipped one.

Property 2

Guards can only reduce permission

A ToolGuard returns either a denial reason or undefined. There is no “allow” return value at all. The docs say why: “because guards have no allow result, listener ordering cannot turn a denial back into permission.”

So a residency rule written as a guard cannot be defeated by a later plugin, a Marketplace install, or a badly ordered configuration. It is not a convention. It is a type.

Property 3

Arguments cannot be rewritten

The pre-execute decision type deliberately has no “rewrite the input” option. The docs give the reason: “arguments are already logged and presented … history, audit, UI and execution must agree.”

You cannot quietly change what a tool was asked to do. You can only allow it, refuse it, or ask a human. For an auditable system, that restriction is a feature.

07

Capability seams — the part that makes sovereignty a configuration change

If you remember one technical concept from this page, make it this one.

Verified — architecture.md The definition

A seam is a swappable capability with three roles: a Service Definition declaring the interface, a Service Provider implementing it, and a Consumer using it — commonly a model-facing tool. A package may combine roles, but one role alone is not a seam; adding a capability means designing all three.

Now the sentence that should make a sovereign-cloud company sit up. It is the project’s own example, not mine:

Verified — architecture.md

“Seams are why one provider swap changes the whole product. Filesystem and subprocess providers share one execution world, so pointing them at a remote sandbox moves Bash, PTY, and LSP with them, with no provider forks.”

Read it slowly. The Bash tool does not know where the shell runs. The terminal does not know where the terminal is. The code-navigation tool does not know which machine holds the code. They all ask ctx.fs and ctx.subprocess. Replace those two providers and every one of those tools relocates — without a single line changing inside any tool.

The project already ships proof of this. There is an e2b package that owns one shared remote Linux sandbox handle, and two providers — fs-e2b and subprocess-e2b — that inhabit that same runtime. It is the identical manoeuvre Magna needs, aimed at a different destination.

The seams that exist today

The project publishes a catalogue of every service, its role, its owner and its implementations. These are the ones that matter to Console. All of them are Verified from that catalogue.

The Magna version of the sentence

Point ctx.fs and ctx.subprocess at the Riyadh cluster, compose no ctx.web provider on the Private tier, and register the four on-premise models on ctx.llm. The whole product is now on-premise. Bash still works. The terminal still works. Code navigation still works. Every tool a customer installs from the Marketplace tomorrow is on-premise too, automatically, because it can only reach the world through seams you already own.

That is what “Egress today: 0 bytes” would mean if it were a measurement instead of a label.

Five concrete Magna integrations

Each one is tied to something Console already does. Each one is a file. Read the badges: Verified means the interface is documented in the repository; Proposed means it is my design and does not exist yet.

First, the shape every plugin has

All five follow the same pattern, which I took from a real plugin in the repository (packages/context/time-context). Learn this once and the rest is detail.

the anatomy of a dsh plugin — pattern verified from repository source
import type { Context } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'

// 1. A name. Loader diagnostics use it; session events can be attributed to it.
export const name = 'magna-example'

// 2. What this plugin needs. Cordis waits until these services exist,
//    and unloads this plugin cleanly if they go away. No boot ordering code.
export const inject = ['tools', 'approval']

// 3. Typed, validated configuration. Bad values fail the plugin load,
//    not the first request at 03:00.
export interface Config { region: string }
export const Config: z<Config> = z.object({ region: z.string().required() })

// 4. The body. Everything registered here is an EFFECT: it returns a
//    disposer, and it unwinds when this plugin unloads.
export function apply(ctx: Context, config: Config): void {
  // ctx.on(...)        listen to a typed event
  // ctx.tools.register(...)   add a tool
  // ctx.llm.registerAdapter(...)  add a model
}

1 — The on-premise model adapter Proposed, on a verified interface

Console today: the Models window lists Kimi K2 Instruct, DeepSeek V3.1, Qwen 3 235B and NVIDIA Nemotron 120B, all on magna-riyadh-dc1 · 8×H200, plus a router that sends short factual questions to Nemotron, Arabic drafting to Qwen 3, and code and SQL to DeepSeek.

In dsh: a model provider is registered on ctx.llm. The interface is an abstract class LlmAdapter with exactly one required method, stream(). That is verified. What is below it is my implementation sketch.

packages/magna-llm-riyadh/src/index.ts
import type { Context } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'
import { LlmAdapter, attributionHeaders } from '@deepseek-ai/dsh-llm'
import type { GenerateOptions, StreamChunk, LlmProviderInfo } from '@deepseek-ai/dsh-llm'

export const name = 'magna-llm-riyadh'
export const inject = ['llm']                    // wait for ctx.llm

export interface Config { baseUrl: string }
export const Config: z<Config> = z.object({ baseUrl: z.string().required() })

class RiyadhAdapter extends LlmAdapter {
  constructor(private readonly baseUrl: string) { super() }

  providerInfo(provider: string): LlmProviderInfo {
    return { id: provider, name: 'Magna Riyadh DC-1' }
  }

  // The ONLY required method. It yields the harness's raw chunk protocol.
  async *stream(options: GenerateOptions): AsyncIterable<StreamChunk> {
    const res = await fetch(`${this.baseUrl}/chat/completions`, {
      method: 'POST',
      signal: options.signal,                    // adapters MUST honour this
      headers: { 'content-type': 'application/json', ...attributionHeaders() },
      body: JSON.stringify(toWire(options)),     // your OpenAI-compatible payload
    })

    // translate the server-sent events into the harness vocabulary:
    //   block-start / text-delta / reasoning-delta / tool-call-delta / block-end
    for await (const sse of readServerSentEvents(res)) yield* translate(sse)

    // CONTRACT, verified in docs/subsystems/llm-streaming.md:
    //   usage comes BEFORE finish, and NOTHING comes after finish.
    yield { type: 'usage',  usage: countTokens() }
    yield { type: 'finish', reason: 'stop' }
  }
}

export function apply(ctx: Context, config: Config): void {
  // One adapter instance can serve several provider routes.
  // Registration is all-or-nothing and is disposed with the plugin.
  ctx.llm.registerAdapter(
    ['magna-kimi-k2', 'magna-deepseek-v31', 'magna-qwen3', 'magna-nemotron'],
    new RiyadhAdapter(config.baseUrl),
  )
}
Verified Adapter rules you must obey, from the docs

• Usage before finish, nothing after finish.
• Tool-call arguments stay raw JSON strings end to end — a provider that returns parsed objects must re-stringify at block-end.
• One adapter call is one provider attempt. Adapters disable library retries; recovery happens at the agent level in a new durable turn.
• Context overflow has one canonical code (CONTEXT_WINDOW_EXCEEDED). Consumers route on the code, never on provider text.
• An empty completion is a retryable error, not a silent success.

Those five rules are exactly the class of bug a team discovers three months into writing their own harness. Here they are written down and enforced by the type system.

The cheap first version

If Magna’s cluster already exposes an OpenAI-compatible endpoint (vLLM, SGLang and TGI all do), you may not need to write an adapter at all on day one. The project’s own Python SDK guide documents DEEPSEEK_BASE_URL for “an OpenAI-compatible proxy rather than the default DeepSeek endpoint”, and the Web UI’s model settings page covers “custom OpenAI-compatible endpoints”. Point the shipped adapter at Riyadh, prove the loop, and write a native adapter later when you want Magna-specific routing and cost metering. Verified that the option exists — I have not tested it.

2 — Console’s approval bar, as a tools/pre-execute waterfall Proposed, on a verified interface

Console today: an OS-wide approval bar. Any app about to write something calls one function, which shows one bar with a title, a detail line, Cancel and a confirm button. The design note in Console’s own source says it is “the thing that makes ‘nothing irreversible happens without your yes’ true by construction rather than per-feature.”

In dsh: that is two listeners. The first decides which calls need a human. The second is the human channel. Splitting them this way matters, because the approval service writes a durable approval/asked + approval/decided audit pair — which a plain deny would not.

packages/magna-approval-bar/src/index.ts
import type { Context } from '@deepseek-ai/cordis'
import type { ToolExecution, PreToolDecision } from '@deepseek-ai/dsh-tools'
import type { ApprovalRequest, ApprovalOutcome } from '@deepseek-ai/dsh-user-approval'

export const name = 'magna-approval-bar'
export const inject = ['tools', 'approval', 'agents']

export function apply(ctx: Context, config: Config): void {

  // ---- A. WHICH calls need a human? -------------------------------------
  ctx.on('tools/pre-execute', async (exec, next): Promise<PreToolDecision> => {

    // Reads are free. Delegate — let the rest of the chain decide.
    if (!isWrite(exec)) return next()

    // Autonomy level 3 agents on an allow-listed tool: also delegate.
    if (autonomyOf(exec.agent) >= 3 && config.allowList.includes(exec.name)) {
      return next()
    }

    // Everything else asks. 'ask' runs ONLY after the approval service
    // answers 'allowed-once'; every other outcome denies.
    return { kind: 'ask', reason: describeWrite(exec) }
  })

  // ---- B. WHO answers? Console's bar. -----------------------------------
  ctx.on('approval/request', async (req: ApprovalRequest, next): Promise<ApprovalOutcome> => {
    // Only answer for agents this bridge owns; otherwise delegate.
    if (!ownsAgent(req.agent)) return next()

    // Push the question to the browser over the open WebSocket and wait.
    // req.callId names the tool call Console already streamed, so the bar
    // attaches to that card instead of rendering a second copy.
    const answer = await consoleBar.ask({
      sessionId: req.agent.session.id,
      callId:    req.callId,
      toolName:  req.toolName,
      reason:    req.reason,
      signal:    req.signal,      // aborting withdraws the question
    })

    return answer === 'approve' ? 'allowed-once' : 'rejected'
  })

  // ---- C. Nothing else is needed. ---------------------------------------
  // If this plugin unloads, both listeners unwind, no answerer remains,
  // and every ask resolves 'unavailable' — which DENIES. Fail-closed by
  // construction, not by a flag somebody might forget to set.
}

What you get for free

The audit pair on the session log. The per-session policy: ask delegates to answerers, never deterministically rejects without asking anyone — which is exactly what an unattended overnight run should use.

And the guarantee that a listener registered later, even with prepend, cannot bypass the never policy, because it is enforced inside the service before dispatch.

What you must build

consoleBar.ask(). That is the browser bridge, and it is the real work — see section 9. Everything above it is twenty lines.

Also isWrite(). Console already has this knowledge in its connector permission lists (po:read allowed, po:write denied). Move that table into the plugin.

3 — The residency guard and the receipt Proposed, on a verified interface

Console today: a Sovereignty widget reading Egress today: 0 bytes, a Private and a Public tier, and a residency receipt attached to individual answers.

In dsh: two pieces. A guard for enforcement, because a guard can only ever reduce permission. And a tools/result observer for the receipt, because that is where the frozen, authoritative outcome appears.

Note the order of preference. The strongest form of this rule is not a guard at all — it is composition. If the Private tier composes no ctx.web provider, the fetch and search tools do not exist, so there is nothing to deny. The guard is the second line, for tools that arrive later.

packages/magna-residency/src/index.ts
import type { Context } from '@deepseek-ai/cordis'
import type { ToolExecution, ToolExecutionResult } from '@deepseek-ai/dsh-tools'

export const name = 'magna-residency'
export const inject = ['tools', 'sessions']

export function apply(ctx: Context, config: Config): void {

  // ---- 1. ENFORCE ------------------------------------------------------
  // A ToolGuard returns a denial reason, or undefined to abstain.
  // There is NO allow return value: nothing downstream can re-permit it.
  ctx.tools.guard((exec: Readonly<ToolExecution>) => {
    const destination = residencyOf(exec.name)          // your tool → provider map

    if (destination === 'in-country') return undefined  // abstain, stay allowed

    return `Residency policy: ${exec.name} would send data to ${destination}. `
         + `The Private tier permits 0 bytes of egress. Use an in-country `
         + `equivalent, or switch this session to the Public tier.`
  })

  // ---- 2. RECORD -------------------------------------------------------
  // tools/result carries the frozen, lossless final outcome. Observers
  // cannot change it — which is exactly what you want in an audit path.
  ctx.on('tools/result', (exec, result: Readonly<ToolExecutionResult>) => {
    exec.agent?.session.append('magna/residency-receipt', {
      callId:      exec.callId,
      tool:        exec.name,
      provider:    providerOf(exec.name),
      region:      config.region,          // 'sa-riyadh-1'
      egressBytes: 0,
      failed:      result.isError,
    })
  })
}
Two things this design has to respect

Adding a durable event is a declared step, not an ad-hoc write. The architecture map says: to add durable session state, extend SessionEventMap, then render and replay from the log. magna/residency-receipt above assumes that declaration exists. Verified requirement.

A receipt is log-only, not model-visible. Because “model-visible means logged”, the reverse is not true: appending an event does not put it in the model’s context. That is the behaviour you want here — the receipt is for the human and the auditor, and it should not consume tokens. If you ever do want the model to know, that is a different mechanism (agent.inject()).

Where I would push back on the label

Egress today: 0 bytes is currently text in a prototype. Under dsh it could become a measurement — but only if the counting happens at the seam that actually touches the network, not at the tool name. A tool called read_local_file that quietly resolves a remote URL would pass a name-based check. So the residency map must be derived from which provider serves the call, and the honest version of the widget reads its number from the session log, not from a counter in the browser.

packages/magna-catalog/src/index.ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'magna-catalog'
export const inject = ['skills', 'commands']

export function apply(ctx: Context, config: Config): void {

  // ---- Console's installed skills become model-invocable skills --------
  ctx.skills.registerProvider(({ signal, invalidate }) => ({
    name: 'magna-marketplace',
    async list() {
      // clause-finder, ar-en-brief, p6-slip-report, minutes-to-actions …
      const installed = await magnaCatalog.installedSkills({ signal })
      return installed.map(toSkillSummary)
    },
  }))

  // ---- Console's "/" commands run WITHOUT spending a model turn --------
  ctx.commands.register({
    name: 'residency',
    description: 'Show where this session ran and how many bytes left the network.',
    handler: ({ agent }) => ({
      kind: 'success',
      text: renderResidencyReceipt(agent.session),   // read from the log
    }),
  })

  ctx.commands.register({
    name: 'tier',
    description: 'Switch this session between the Private and Public tiers.',
    input: { hint: 'private | public' },
    handler: async ({ agent, rawInput, signal }) => {
      const tier = rawInput.trim()
      if (tier !== 'private' && tier !== 'public') {
        return { kind: 'error', text: 'Use /tier private or /tier public.' }
      }
      await setTier(agent, tier, signal)
      return { kind: 'success', text: `This session is now on the ${tier} tier.` }
    },
  })
}
Why “without a model turn” matters

A command handler runs directly against the receiving agent. It does not become a message, it does not cost tokens, and it cannot be misread by the model. /residency in Console should be instant and exact. This is the mechanism that makes it so.

The lifecycle is still logged — command/run before the handler and command/done after — so the audit trail sees it even though the model does not.

5 — Overnight agents on ctx.jobs Proposed, on a verified interface

Console today: three Automations — “P6 slip heartbeat” daily at 06:00 AST, “Board pack scheduler” Thursdays 07:00, “Vendor duplicate sweep” weekly — and a “while you were away” summary at sign-in.

In dsh: ctx.jobs is the background-work registry. A producer declares a kind, a label, an owner and a run() that returns three hooks. The runtime owns identity, access and lifecycle; the producer owns the actual work.

packages/magna-automations/src/index.ts
import type { Context } from '@deepseek-ai/cordis'
import type { Agent } from '@deepseek-ai/dsh-agent'
import type { JobHooks, JobOutcome } from '@deepseek-ai/dsh-jobs'

export const name = 'magna-automations'
export const inject = ['jobs', 'agents', 'sessions', 'commands']

export function apply(ctx: Context, config: Config): void {

  function startAutomation(agent: Agent, spec: AutomationSpec) {
    const abort = new AbortController()

    return ctx.jobs.start({
      kind:  'magna-automation',   // extends JobKindMap; also the id prefix
      label: spec.name,            // "P6 slip heartbeat" — one model-facing line
      owner: agent,                // access is fenced by this agent's session id,
                                   // and disposing the agent cancels and awaits it
      run: (): JobHooks => {
        const work = runAutomation(spec, abort.signal)
        return {
          // must be synchronous, idempotent, and eventually settle done
          cancel: (reason) => abort.abort(reason),
          // resolves only after resources are RELEASED, not when work ends
          done: work.then((o): JobOutcome => ({
            status: o.ok ? 'completed' : 'failed',
            detail: o.summary,           // "3 activities slipping > 5 days"
          })),
          // present = a streaming job; absent = final output only
          readOutput: () => work.drainSinceLast(),
        }
      },
    })
  }

  // ---- "While you were away" ------------------------------------------
  // At sign-in, Console asks for the night's jobs and renders the digest.
  // Nothing needs to be invented: the snapshots and the session log
  // already hold status, detail, startedAt and finishedAt.
  ctx.commands.register({
    name: 'digest',
    description: 'What ran while you were away.',
    handler: ({ agent }) => ({ kind: 'success', text: renderDigest(agent) }),
  })
}
The overnight design decision you must make deliberately

An unattended job has no human to answer the approval bar. Under the shipped semantics, an ask with no answerer resolves unavailable, which denies. That is safe but silent — the job simply fails at 03:00 and nobody knows why.

The better shape, and the one the harness gives you a name for: run overnight sessions under the never approval policy, so every ask is deterministically rejected rather than left hanging. Then the automations are read-only by construction, they queue their proposed writes, and the human approves the batch in the morning. That is exactly what Console’s automations already claim — “puts the deck in your drafts — never sends it.” The runtime can now make that claim true rather than aspirational. My recommendation, on a verified policy.

How this actually meets the HTML

The question you asked. Here is the honest answer, before the diagram.

The framing that has to run through this whole section

MagnaVERSE Console is a static HTML prototype with no backend. One file, opened in a browser. Every agent, every approval, every model answer in it is simulated in JavaScript.

dsh is a Node.js process. It reads files, spawns processes, holds an append-only log on disk, and talks to model endpoints over the network. A browser cannot do any of those things.

So integration is not “add a script tag to app-7-console.html”. There is no version of this where the harness runs inside the page. Integration means: a process appears, and Console stops simulating and starts asking that process. Everything below is about where that process lives and how the page talks to it.

The four realistic options, and their trade-offs

OPTION A

Use dsh’s own Web UI, and do not integrate at all yet

  • What it is. npx @deepseek-ai/dsh web, open 127.0.0.1:3080, point the model settings at Riyadh. Console is not involved.
  • For. Zero engineering. You learn what the harness actually does in an afternoon, with real tool calls against real repositories. Every claim on this page becomes something you have watched happen.
  • Against. It is not your product. No windows, no sovereignty widget, no Marketplace, no Arabic, no Magna brand. Nothing here is reusable as product code.
  • Verdict. Do this this week. It is a spike, not an option for the product.
OPTION B

Console stays a static file; a Magna plugin inside dsh serves it and talks to it

  • What it is. Write one plugin, magna-console-bridge. It registers routes on ctx.webServer that (1) serve app-7-console.html and (2) open a WebSocket. Over that socket it streams session/event to the browser and carries approval questions back. The approval/request answerer from integration 2 lives in this same plugin.
  • For. Console’s HTML stays a single self-contained file, which is the whole reason it is easy to work on. The approval answerer is in the same process as the tool pipeline, which is what the seam requires. You can build it incrementally — wire the transcript first, the approval bar second, the residency widget third — and Console keeps working in demo mode for everything not yet wired.
  • Against. You depend on ctx.webServer and the event shapes, which are developer-preview surfaces. You must handle authentication yourself. Console must learn to render from a real event stream, which is genuine front-end work.
  • Verdict. This is what I would build. Reasons below.
OPTION C

Rebuild Console as a dsh client bundle

  • What it is. Console stops being a static file and becomes part of the harness’s own web application — its screens registered through the client-module system, its chat surfaces registered as conversation nodes, its settings as settings cards. The architecture map lists all of these as documented extension points.
  • For. The highest fidelity. Hot reload, the harness’s own streaming, no bridge to maintain, and Magna features appear inside the harness’s UI conventions instead of beside them.
  • Against. It is a rewrite, and it couples Magna’s release cycle to a six-day-old project that has promised breaking changes. Console’s window manager, RTL work and brand system would have to be rebuilt inside someone else’s application shell.
  • Verdict. Not now. Revisit once the preview ends and the client-module surface has been stable for a couple of releases.
OPTION D

Drive dsh from a Magna backend through the SDK

  • What it is. Magna writes its own API. That API drives a harness runtime as a subprocess over stdio JSON-RPC, using the published TypeScript SDK (@deepseek-ai/dsh-sdk-client) or the Python SDK (pip install deepseek-harness-sdk). Console talks only to Magna’s API and never sees dsh.
  • For. The loosest coupling. A breaking change upstream costs you one adapter, not your product. It is the natural shape for multi-tenant SaaS, and for batch work that no human is watching.
  • Against, and this one is decisive. The SDK client’s own README lists, under known limitations: “Client→server notifications and server→client requests are unimplemented on both wire ends; the transport carries them for future approval flows.” In plain words: the harness cannot currently ask a question back through the SDK wire. There is also no mid-turn cancel. An approval bar in a browser cannot be answered this way today.
  • Verdict. Right for overnight and batch work, where the approval policy is never and nobody is being asked anything. Wrong for the interactive product, until those wire methods land.
The recommendation, and the reasoning

Option A this week. Option B for the product. Option D for the automations. Option C reconsidered in six months.

The deciding argument is the approval bar, because it is Console’s most important promise. An approval answerer is a Cordis listener — it lives inside the harness process, beside the tool pipeline, and it must return an outcome synchronously enough to hold the tool call open. If Magna’s own API sits between the browser and the harness (Option D), that question has no way home today; the SDK README says so explicitly. Option B keeps the answerer in-process and gives it a direct socket to the human. Everything else — residency, MCP, skills, jobs — works under either option; approval is what chooses.

The second argument is reversibility. Option B is one plugin and one WebSocket. If the harness turns out to be the wrong bet in six months, you delete a plugin and Console reverts to what it is today. Option C would leave you with a rewrite you could not undo.

Why this is notable — and what could go wrong

Both halves, honestly. A brief that only contains the good half is a sales document, not a technical one.

Six things that are genuinely good

MIT, with no strings

Magna sells a self-hosted product to customers. That combination defeats most reassuring arguments about copyleft. MIT does not care: keep the notice, ship what you like, change what you like, do not disclose your source. For a company shipping a sovereign deliverable, this is the licence you want.

No privileged core

The model adapter, the tool registry, the session log and the agent loop are all plugins. Every substitution Magna needs is a configuration row rather than a fork. You keep taking upstream releases while running a product whose important code paths are your own.

Reversible effects

Every registration returns its exact disposer. Turning a capability off is an operation, not a restart and a hope. For per-tenant licensing, emergency connector shutdown, and residency modes that must genuinely remove tools, this is the difference between a policy and a promise.

The log is the context

“Model-visible means logged”, enforced by a runtime invariant. There is no hidden place for context to live. Every answer can be reconstructed from disk, in order, with the tool calls that produced it. This is the property a regulated customer will ask about, and most agent stacks cannot answer.

Composition that is inspectable

Profiles stack bundles, patches replace rows by id, and dsh --profile web --dump-config prints the exact tree that boots. “What is running in production?” has a command-line answer. That is unusual and it is worth a lot during an incident.

Batteries you would otherwise build

MCP client, skills, subagents, workflows, compaction, background jobs, sandbox policy, permission presets, LSP, PTY terminals, JSONL and SQLite session backends, OpenTelemetry. Each of those is weeks of work you do not do.

Six things that could go wrong

1 · Developer preview means what it says

The README promises compatibility-breaking changes, in capital letters. Interfaces on this page will move. Plan for a version pin, a paid upgrade budget every few months, and a test suite that fails loudly rather than silently.

2 · The project is six days old

Created 13 August 2026. There is no track record, no long-lived security history, no body of production war stories. The star count measures curiosity. Do not confuse it with a maturity signal, and do not let anyone else in the building confuse it either.

3 · You adopt Cordis too

Choosing dsh means choosing a whole programming paradigm: contexts, services, injection, typed events, effects. That is a real learning curve for a team used to plain Node. It is also a second dependency whose future you do not control. Budget training, and expect the first two Magna plugins to be slow.

4 · The interactive gap is real

The SDK cannot yet carry a server-to-client question or a mid-turn cancel. That is not a theoretical limitation — it directly constrains the architecture, as section 9 shows. If your plan depends on driving the harness from a Magna backend while a human approves in a browser, that plan does not work today.

5 · Sovereignty is a composition discipline, not a switch

Nothing in dsh stops you from composing a plugin that phones home. The guarantee comes from what you do not compose, plus guards for what arrives later. That discipline has to be enforced in CI — a build that fails when the Private profile’s dumped config contains a network provider — or it will erode within a year.

6 · It is a DeepSeek project

Worth stating plainly for a Saudi enterprise buyer: this is open source under MIT and runs entirely on your hardware, so no data goes to DeepSeek. But the governance, the roadmap and the release cadence belong to one vendor. Some customers will ask. Have the answer ready, and have the fork-and-freeze plan ready too — MIT makes that possible.

A staged adoption path

Nothing here commits Magna to anything until stage 3. That is deliberate.

WEEK 1

Prove it runs, on your hardware, with your models

  • Run npx @deepseek-ai/dsh web on one machine inside the DC. Open 127.0.0.1:3080.
  • Point the model settings at a Riyadh endpoint. Try the shipped adapter with a custom OpenAI-compatible endpoint before writing any code.
  • Give it a real task on a real repository. Watch the tool calls. Watch the approval prompts.
  • Run dsh --profile web --dump-config and read the tree. This is the single most useful hour in the whole evaluation.
  • Exit test: can one engineer explain the turn and the tool pipeline to a colleague, from what they watched rather than from this page?
WEEKS 2–3

Write two plugins and find out what it costs

  • Plugin one: the residency guard from integration 3. It is about thirty lines and it exercises the guard interface, the configuration schema and the effect lifecycle.
  • Plugin two: one MCP server from Console’s Marketplace — p6-schedule is the obvious candidate — wired through dsh-mcp-client. This is configuration only, so it measures how much you get without writing code.
  • Deliberately break something: unload a plugin mid-session and confirm its registrations really unwind.
  • Exit test: a written estimate, in days, for the magna-console-bridge plugin. If nobody can produce that number, you have not learned enough yet.
MONTH 2

The pilot: one Console window, one real workflow, ten users

  • Build magna-console-bridge. Wire exactly one Console surface to it — I would choose the chat window, because it exercises streaming, tools and approval together.
  • Everything else in Console stays in demo mode. Users should be able to tell which is which.
  • Pick one workflow with a real owner. “P6 slip heartbeat” is a good pilot: read-only, valuable, and its failure mode is a missed alert rather than a wrong write.
  • Pin the exact version. Read every release note. Keep a written log of every breaking change and what it cost to absorb.
  • Exit test: after four weeks, is the total cost of upstream churn under one engineer-day per week? If not, stop and reassess — that number will not improve by itself.
BEFORE PRODUCTION

Nine things that must be true

  • 1. The developer-preview warning is gone from the README, or Magna has accepted a named owner for absorbing breaking changes indefinitely.
  • 2. A CI gate fails the build if the Private profile’s dumped configuration contains any provider that can reach the public internet.
  • 3. A security review of the sandbox and approval path, done by someone who did not write the plugins.
  • 4. A licence audit of the full dependency tree, from THIRD_PARTY_NOTICES.md outwards — the same gate the rest of the stack already passes.
  • 5. The session log has a retention, encryption and export policy, agreed with legal. It contains everything, which is its strength and its risk.
  • 6. A tested restore: kill the process mid-turn, restart, and confirm the session resumes from the log with nothing invented.
  • 7. Load and cost figures from a real week, not a demo. Steps, tokens, and SAR.
  • 8. An exit plan written down. Under MIT you may fork and freeze; know in advance which version you would freeze at and who would maintain it.
  • 9. Arabic and RTL verified end to end — not just in Console’s UI, but in tool results, file paths and the transcript renderer.
